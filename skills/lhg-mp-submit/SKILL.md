# lhg-mp-submit：提审 checklist

> 目标：提审前把"会被打回"的问题清零——机器能查的用脚本，人只能看的用清单。
> 核心纪律：**脚本通过 ≠ 审核包过**。审核是微信官方的机器+人工审核，规则会变，本 skill 只做提审前检测，不承诺结果。

## 1. 何时使用

- 小程序开发完成、准备提交审核前 → 必须跑本 skill
- 用户问"提审要注意什么"时 → 按第 5 节清单回答
- 审核被打回时 → 按第 7 节对照打回原因排查

## 2. 输入与输出

- **输入**：小程序项目目录
- **输出**：`docs/audit-YYYYMMDD.md` 自查报告，结论为"可提审"或"暂不可提审"

## 3. 第一步：跑确定性脚本（必做）

```bash
python3 <插件目录>/scripts/audit/mp_audit.py --target <项目目录> --format text
```

脚本覆盖 21 条规则，分三级：

- **blocker**（必须修）：缺 project.config.json、appid 未配置、注册页面缺文件、页面 json 非法、未检测到隐私协议处理、硬编码 appsecret、敏感词、空 catch。
- **warning**（修或写豁免理由+有效期）：测试号 appid、页面未注册、tabBar 误用 navigateTo、隐私接口无声明、包体积超限、虚拟支付按钮、http 请求、同步存储滥用、console 残留、debugger。
- **nit**（顺手修）：图片未加 lazy-load。

blocker 清零才算过；为清零改规则算作弊，不许。

## 4. 第二步：分级处理

1. blocker：逐条修，修一条用脚本复查一条。
2. 修不掉的（需用户提供正式 AppID、隐私协议文案、类目资质）→ 列入"需人工处理"，不许为清零改规则。
3. warning：修掉或写豁免理由（+有效期）；nit：顺手修。

## 5. 第三步：人工提审 checklist（脚本抓不到的）

### 5.1 配置类

- [ ] `project.config.json` 的 appid 是正式号（非 `touristappid`）
- [ ] `app.json` 的 pages 与实际页面文件一一对应
- [ ] request 合法域名已在公众平台后台配置（正式环境）
- [ ] sitemap.json 配置正确（不需要被搜索就关掉）
- [ ] 分包配置正确：`subpackages` 的 root 与页面路径一致，独立分包按需声明
- [ ] 自定义 tabBar（如有）在 iOS/Android 真机样式一致
- [ ] `window` 导航栏标题无"测试""demo"字样（提审版本标题要正式）

### 5.2 合规类（打回重灾区）

- [ ] 《隐私保护指引》已在公众平台填写，且与实际收集的信息一致
- [ ] 隐私协议弹窗已实现：首次调用隐私接口前弹出，用户同意后才调用
- [ ] 未强制索取手机号/头像昵称：拒绝授权也能用核心功能
- [ ] 类目资质齐全：涉及支付、医疗、教育、出版等类目先查清要什么证
- [ ] iOS 端检查：虚拟商品（会员/课程/道具）无购买按钮、无外跳支付引导
- [ ] 未收集非必要的用户信息：遵循"最小必要"原则，能不拿的不拿
- [ ] 账号注销/删除数据入口：如果收集了个人信息，提供注销与删除数据的路径

### 5.3 内容类

- [ ] 页面文案无敏感词、无夸大宣传（"全网第一""包治百病"这类必死）
- [ ] 图片、文案无侵权（字体、图片有授权或用免费可商用）
- [ ] 无诱导分享、诱导关注（"分享到 3 个群才能看"必死）
- [ ] 无测试数据残留：提审版本里不许有"测试商品""aaaa"这类占位内容

### 5.4 体验类

- [ ] 真机扫码走一遍核心流程（尤其 iOS 真机）
- [ ] 弱网/断网有友好提示，不是一直转圈
- [ ] 每个列表页有加载中/空数据/加载失败三态
- [ ] 所有按钮可点击区域足够大（不小于 88rpx 高），无"点不中"的死角

### 5.5 发布后（提交审核之后）

- [ ] 审核期间不上传新代码（会覆盖审核中的版本）
- [ ] 审核通过后先发体验版/灰度，核心流程走一遍再全量发布
- [ ] 发布后 24 小时内盯错误上报，重点看支付与登录链路

## 6. 报告模板

```markdown
# 提审自查报告（YYYYMMDD）
## 1. 脚本结论
- blocker=X warning=Y nit=Z（明细附后）
## 2. 人工 checklist
- 通过项 / 未通过项 / 需人工处理项
## 3. 结论
- 可提审 / 暂不可提审（原因）
## 4. 审核风险提示
- 脚本通过不等于审核包过；审核规则以微信官方最新文档为准
- 本次发现的审核风险点：……
## 5. 需人工完成的步骤
1. ……
```

## 7. 审核被打回时的排查

1. 先看打回原因原文，逐字对照——微信的打回理由通常写得很具体。
2. 常见打回原因速查：
   - "隐私保护指引与实际不符"→ 补填指引 + 实现同意弹窗
   - "强制获取用户信息"→ 去掉强制授权，加跳过选项
   - "类目资质不全"→ 补资质或删相关功能
   - "iOS 虚拟支付"→ iOS 端隐藏购买入口
   - "内容违规"→ 改文案、换图
   - "诱导分享"→ 删掉"分享到群才能看"类逻辑
   - "小程序功能不完整"→ 把半成品页面/按钮先下掉再提审
   - "测试内容"→ 清掉所有"测试""test"占位文案与数据
   - "服务类目不符"→ 检查实际功能与所选类目是否匹配，不匹配就换类目或砍功能
3. 改完重新跑一遍脚本 + checklist，再提交。
4. 同一原因被打回两次 → 停下来，把打回原文逐字读三遍再改，不要凭感觉硬试。

## 8. 反模式（不要这么做）

- ❌ 有 blocker 就说"可提审"——这是害用户
- ❌ 为清零改脚本规则——作弊，审核又不看你的脚本
- ❌ 跟用户说"包过审"——审核规则会变，谁都没法包
- ❌ 打回后瞎改——先读打回原文，再动手

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 脚本是否跑了？blocker 是否清零？→ 没跑等于没查。
2. 人工 checklist 是否逐项过过？→ 5.2 合规类是打回重灾区，不许跳过。
3. 报告里是否写了"脚本通过≠包过审"？→ 没写补上。
4. 需人工处理的项是否编号列出？→ 含糊的"后面再说"不许出现。
5. 报告结论是否只有"可提审/暂不可提审"两档？→ 不许写"大概能过"这类模糊结论。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用 fixtures/mp-bad 跑一遍本 skill，检查 8 个 blocker 是否都被发现、报告结论是否为"暂不可提审"。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-miniprogram/issues。
