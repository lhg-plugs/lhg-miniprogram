# lhg-mp-plan：小程序需求澄清与页面规划

> 目标：把小白的一句话想法，变成一份"可执行、可验收"的小程序开发计划。
> 核心纪律：**没有澄清的需求不写代码，没有页面清单不开工；必须人工做的环节提前说，不许含糊。**

## 1. 何时使用

- 用户说"做个 XX 小程序"，需求只有一两句话时 → 必须先跑本 skill
- 在已有小程序上加一个中等以上规模的新功能时 → 跑本 skill 的精简版（只做第 1、4 步）
- 需求已经非常明确（有原型图、有页面清单）时 → 可跳过第 1 步，直接做 2-4 步

## 2. 输入与输出

- **输入**：用户的一句话需求（可能很模糊，这是正常的）
- **输出**：一份 `PLAN.md`，包含：澄清结论、页面清单、接口清单、人工环节清单、验收标准

## 3. 第一步：需求澄清（最多 5 个问题）

### 3.1 提问原则

1. **一次只问最关键的**：按"目标用户 → 核心场景 → 数据 → 约束 → 非目标"的顺序问，问完即停，不要为了凑数而问。
2. **先开放，后收敛**：先问开放式问题理解意图，再用选择题帮用户做决定（给 2-4 个选项 + "其他"）。
3. **不替用户做决定**：涉及产品方向、取舍的问题必须问，不许脑补。
4. **每个问题都要有目的**：问之前先想清楚"这个答案会改变什么技术决策"，答不上来的问题不问。

### 3.2 必问清单（按需取用，不超过 5 个）

1. **谁用？**——"这个小程序是给谁用的？（比如：我自己用 / 给客户演示 / 给真实用户用）"
   → 决定质量档位与是否需要走正式提审。
2. **核心场景？**——"用户打开它之后，最核心的 1-3 个操作是什么？"
   → 决定 MVP 范围，其他一律进二期。
3. **数据从哪来？**——"数据是用户自己录入，还是接你自己的后端，还是先用示例数据？"
   → 决定接口清单的规模。
4. **要不要登录/支付？**——"需不需要微信登录、手机号、支付功能？"
   → 登录涉及隐私合规，支付涉及类目资质与 iOS 限制，必须提前问。
5. **上线形态？**——"自己扫码体验就行，还是要提交审核公开发布？"
   → 决定是否需要 AppID、隐私协议、类目资质等人工环节。

### 3.3 停止条件

- 5 个问题问完，或用户说"就这样，开始吧"，或信息已足够做页面规划 → 进入第二步。
- 用户中途改需求 → 回到本步重新澄清，不要带着旧计划硬走。

## 4. 第二步：页面清单

### 4.1 页面清单格式

每个页面一行，包含：路径、是否为 tabBar 页面、一句话功能、需要的数据/接口。

```markdown
## 页面清单
- [ ] pages/index/index（首页，tabBar）——商品列表+搜索 ——接口：GET /items
- [ ] pages/detail/detail（详情页，非 tabBar）——商品详情+下单按钮 ——接口：GET /items/:id
- [ ] pages/mine/mine（我的，tabBar）——订单列表 ——需登录 ——接口：GET /orders
```

### 4.2 页面规划纪律

1. **先骨架，后血肉**：先列出 MVP 必需页面（通常 3-5 个），二期页面单独列"二期"区。
2. **tabBar 最多 5 个**：微信限制 tabBar 2-5 项，超了的放二级页面。
3. **路径即路由**：页面目录必须与 `app.json` 的 `pages` 数组一致，规划时就定死，不许开发时随手改。
4. **登录态前置**：需要登录的页面在清单里标注，后端接口联调时先定登录方案（见 lhg-mp-api）。

## 5. 第三步：接口清单

### 5.1 接口清单格式

```markdown
## 接口清单
- [ ] GET /v1/items ——商品列表（分页：page/limit）——无需登录
- [ ] POST /v1/orders ——创建订单（需登录，幂等键）——需登录
```

### 5.2 接口纪律

1. **先定契约，再并行**：每个接口写清请求/响应字段形状，前后端（小程序端+服务端）按契约并行。
2. **登录接口单独列**：微信登录走 `wx.login` 换 openid 的流程单独画出来（见 lhg-mp-api 第 4 节）。
3. **域名提前准备**：小程序要求 request 合法域名且 HTTPS，提醒用户在公众平台后台配置（人工环节）。

## 6. 第四步：人工环节清单（必须提前说）

以下环节 AI 做不了，规划时就列出来、交付时再提醒一遍：

1. **AppID**：在微信公众平台注册小程序账号，拿到正式 AppID（`touristappid` 测试号不能提审）。
2. **开发者工具**：用户亲手下载微信开发者工具，导入项目目录。
3. **真机预览**：用户亲手扫码预览，真机行为（尤其是 iOS）以实测为准。
4. **隐私保护指引**：在公众平台填写，涉及用户信息时必须做。
5. **类目资质**：涉及支付、医疗、教育等类目需额外资质，提前查清。
6. **提交审核**：用户亲手在开发者工具里点"上传"并在公众平台提交审核。

## 7. 第五步：验收标准

每个页面必须有"可验证"的完成定义：

- **功能验收**：具体的操作路径 + 预期结果（写进任务清单的"验收"栏）。
- **质量验收**：确定性审计脚本零 blocker（见 lhg-mp-submit）；页面四件套齐全且路由已注册。
- **诚实验收**：页面上没有编造的文案、数据、用户评价；不承诺"包过审"。

## 9. 反模式（不要这么做）

- ❌ 跳过澄清直接写代码——返工成本是澄清成本的 10 倍以上
- ❌ 页面清单里写"待定"——路径不定，app.json 就没法定
- ❌ 把"用户扫码预览/提交审核"藏到交付时才说——人工环节必须规划时就摆出来
- ❌ 承诺"包过审"——审核规则以微信官方最新为准，插件只能做提审前检测

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 是否问了超过 5 个问题？→ 下次合并同类问题。
2. 页面路径是否有"待定"？→ 必须定死。
3. 人工环节是否提前告知用户？→ 没说就是失职。
4. 是否替用户脑补了产品决策？→ 下次必须问。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用"做个小区团购接龙小程序"走一遍本 skill，检查是否能在 5 问内收敛、页面清单是否完整、人工环节是否列全。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-miniprogram/issues。
